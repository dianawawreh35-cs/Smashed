# House rules for every task in this folder

Read this before starting any prompt in `docs/prompts/`. It is what the project
has learned the hard way. The prompts assume it rather than repeat it.

## Before you write code

- Read `docs/DEVELOPING.md`, how to run the three parts and the traps on this
  machine.
- Read the "How this project is tracked" section of `docs/DECISIONS.md`, and any
  dated entry the prompt names.
- Read the requirement rows the prompt names in
  `docs/SRS-Smashed-Burger-Call-Center.md`. The SRS is the contract. If the code
  and the SRS disagree, stop and say so; don't pick one quietly.
- If the design has a real choice in it, one that changes what the client gets,
  ask me before building. Don't ask about things with an obvious answer.

## While building

- **Requirement IDs go in commit messages and in code comments** (`// A-11`),
  next to the rule they explain.
- **Stop the apps before building.** Both run as `dotnet.exe`, so looking for a
  `CallCenter` process finds nothing. Check with
  `Get-CimInstance Win32_Process -Filter "Name='dotnet.exe'"` and read the
  command line.
- **Start the dev server hidden**, with its output redirected to a file. A
  visible console window has frozen the API before. Check the `bin` dates, so
  you know you are running today's build and not yesterday's.
- Delete stale `net8.0` build folders under the Agent App if they have come back.
- **Filter and page on the server**, never in the browser or the app over a page
  of results (see the 20 Sep entry "filtering a page lies").
- **Phone numbers go through `PhoneNormalizer`** (Shared), and nowhere else.
- **Every label in both languages**, Arabic and English (N-09). The Agent App has
  `AgentAppLabelsTests`; a raw key reaching the screen is a bug.
- **The web app's real check is `npm run build`**, not `tsc --noEmit`. That
  difference once hid a broken production build.
- The server tests run against a real PostgreSQL when
  `ConnectionStrings__Default` is set (see `CallCenterApiFactory`). That is how
  CI runs them on Linux. Write database-backed tests where behaviour depends on
  the database.

## You are probably not the only session working here

Several of these tasks run at the same time, in different windows, **on the same
working copy**. That has already gone wrong once and the damage was real.

**Files nearly every task touches.** Expect to open one and find somebody
else's work in progress:

- `src/CallCenter.AgentApp/App.xaml.cs` — everything registers a service here.
- `src/CallCenter.AgentApp/i18n/ar.json` and `en.json` — everything adds labels.
- `src/CallCenter.AgentApp/Views/HomeView.xaml.cs` — everything adding a screen
  adds a rail section.
- `src/CallCenter.AgentApp/Theme.xaml`, `docs/DECISIONS.md`,
  `docs/TESTING-checklist.md`.

**The rules that follow from that:**

- **Never `git add -A`, and never stage a folder.** Stage files by name, every
  time. A session once swept 117 untracked menu pictures into a three-file
  commit. `src/CallCenter.Server/Data/menu-images/` is untracked deliberately —
  it is generated by seeding — so leave it alone.
- **Never commit a file you did not change.** If a shared file holds another
  session's edits as well as yours and they cannot be separated, commit it and
  **say in the message which parts are not yours**. Do not blur them together.
- **Before you delete anything shared, search for other uses of it.** A session
  removing a label called `unclassified` took an unrelated label of the same
  name in a different section with it, and a raw key reached the agent's screen.
  `AgentAppLabelsTests` now catches exactly that; run it.
- **Check the file times before assuming a session has finished.** If something
  was written in the last hour and it is not yours, another window is live.
  Say so rather than guessing.
- **Build and test before you commit, not before you start.** Somebody else's
  half-finished change may be in your build, and that is normal. If the build
  breaks in a file you never opened, it is theirs — tell me, don't fix it.

## When it is done

- Build everything and run all tests. Report the real numbers and any failures.
- **Update the docs in the same commit:**
  - behaviour or scope changed → the SRS row;
  - a decision, trade-off, deferral or correction → a new dated entry in
    `docs/DECISIONS.md`, placed before the "Open items (live)" section;
  - a migration → `docs/SCHEMA.md`;
  - an open item closed or added → the "Open items (live)" section. Delete
    resolved entries; don't tick them.
- **You cannot see the screens.** For any UI change, add steps to
  `docs/TESTING-checklist.md`: what to open, what should happen, and what it
  means if it doesn't. Then tell me exactly what to open, and ask for a
  screenshot. Don't call UI "done" until I have seen it.
- Commit with the requirement ID in the message. **Don't push** until I say so.
- Explain what you did in plain terms first, then the detail. I'm newer to
  git, CI and Docker than to the app itself.
